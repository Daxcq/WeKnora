## 9.1 适配器：插件变"自己人"

`ProcessConnector`（manager.go:572 起）把 `pluginapi.PluginClient` 包成主机的原生接口：

```go
func (c *ProcessConnector) Parse(ctx, req *types.ReadRequest) (*types.ReadResult, error)   // DocReader 形态
func (c *ProcessConnector) Validate(ctx, config *types.DataSourceConfig) error             // 连接器形态
func (c *ProcessConnector) ListResources(...)
```

效果：**第 4 章 `ProcessDocument` 主流程一行没改**——插件解析器对流水线来说只是"碰巧活在另一个进程里的普通解析器"。这就是**依赖倒置**的实战价值：`convert()` 依赖 `DocReader` 抽象，抽象可由内置 Go 兑现、也可由 Python 插件兑现，流水线其余 3900 行毫不知情。

注册表里存的正是这层"皮"（`internal/infrastructure/docparser/plugin_registry.go:21`）：

```go
func RegisterExternalParser(name string, reader interfaces.DocReader, info types.ParserEngineInfo) error
```

带 `sync.RWMutex` 的 map，读多写少——`ExternalParser()` 用 RLock 并发读。

## 9.2 一份 manifest 翻译成多种主机元数据

`LoadDirectory`（manager.go:65–168）按 `extension_types` 扇出注册：

| extension_types | 注册到 | 元数据转换函数 |
|---|---|---|
| `datasource` | `ConnectorRegistry` | `configMetadata`（244） |
| `document_parser` | `docparser.RegisterExternalParser` | 直接用 manifest 字段 |
| `web_search` | `searchRegistry.RegisterExternal` | `webSearchMetadata`（189） |
| `model_provider` | `provider.RegisterExternal` + `chat.RegisterExternalChat` | `modelProviderMetadata`（212） |

一个插件可以同时声明多种类型（一个进程、多种能力）。model 类型目前只支持 `chat`（85 行校验 `ModelTypes == ["chat"]`）。注册失败时的**Saga 逆序回滚**见第 7 章。

## 9.3 错误与超时的分层

- **业务错误**装进 Response.Error 字段（每个 Response 结构体都带 `Error string`）；
- **传输错误**走 gRPC error（`status.Error(codes.Unimplemented, ...)` 表示插件没实现该方法——见 pluginapi:233 `FetchIncremental` 未实现时的返回）；
- **超时分层**：dial 10s（docker 30s，Docker Desktop 起容器慢——407–412 注释解释了原因）、握手 5s、模型配置校验 10s（92–93）。每类操作一个明确超时，不共用。

## 9.4 连接器领域语义（数据同步的学问）

做数据源方向的核心知识，全部围绕 `FetchAll` / `FetchIncremental` 两个 RPC。

### 游标（cursor）设计

```go
type ConnectorRequest struct {
    Config      json.RawMessage  // 插件自己的配置 schema
    Cursor      json.RawMessage  // 上次同步的位置
    ...
}
type FetchResponse struct {
    Items      []FetchedItem
    NextCursor json.RawMessage  // 主机存起来，下次带上
}
```

cursor 对插件是**不透明 blob**（`json.RawMessage`）——主机不理解、不修改、只传递。状态归插件所有。local-files 示例的 cursor 是"当前文件地图"（路径→hash）。

### 内容指纹与变更检测

local-files 用 **SHA-256 内容 hash** 建 map，增量响应只含变化的文件。设计取舍（文档 113 行）：**重命名 = 删除 + 新增**——不追踪 inode/文件 ID，换来实现简单、跨平台一致。

对照你的领域：这套 hash+diff 与增量重解析的 `ComputeContentHash` **同构**——连接器 hash 文件、knowledge hash chunk。游标思想也可借鉴到文档级增量。

### 墓碑（tombstone）

远端删除的表达：`FetchedItem{IsDeleted: true, ExternalID: "..."}`——只声明"这个 ID 在源头没了"，不带内容。

三层控制：

```
sync_deletions=false        → 墓碑被忽略（只增改）
sync_deletions=true
  deletion_policy=retain    → 默认。保留知识，完成同步，不删派生数据
  deletion_policy=delete    → 走主机正常删除流程（chunk/向量/文件/图/软删）
```

### 失败语义

插件进程崩溃 → **本次同步整体失败** → 主机不产生半成品状态（旧知识、旧 cursor 完好）→ 重试或人工介入。原则：**同步操作要么全成要么全不做，绝不留下"同步了一半"的中间态**。

### 资源模型

`ListResources` 返回树形资源（`Resource{ExternalID, ParentID, HasChildren}`），`ResolveResourceAncestors` 支持从叶子反查祖先链——支持"按目录浏览选择同步范围"的 UI。`ExternalID` 用相对路径（示例 README 说明）保证跨机器稳定。
