# 第 3 章 · 前置课 B：工程模式速成

读懂 WeKnora 代码所需的最小工程模式集。每个模式：直觉 + 最小例子 + 出现位置。

## 3.1 函数是"值"，闭包是"带记忆的函数"

Go 里函数可以存变量、当参数传：

```go
greet := func(name string) { fmt.Println("你好,", name) }
greet("Daxc")
```

**闭包**：函数"记住"它定义时周围的变量：

```go
func makeCounter() func() int {
    count := 0            // 被下面的函数捕获
    return func() int {
        count++           // 每次调用操作同一个 count
        return count
    }
}
c := makeCounter(); c() // 1; c() // 2
```

出现位置：`chat_pipeline/chat_pipeline.go` 的 `buildHandler` 从后往前组装责任链，全靠闭包捕获"链条剩余部分"。

## 3.2 责任链与洋葱模型

每个处理器签名里带一根"接力棒" `next`：

```go
func logMiddleware(next Handler) Handler {
    return func(msg string) {
        fmt.Println("[日志] 收到:", msg)  // next 之前：进来时
        next(msg)                        // 放行
        fmt.Println("[日志] 处理完毕")     // next 之后：回去时
    }
}
```

洋葱要点：

- **组装必须从最里层开始**（"穿衣服从里往外"）——想包住别人，得先有别人。这就是 `buildHandler` 从最后一个插件往前循环的原因；
- **不调 `next()` = 短路**：门不开，内核及之后全部不执行。`search.go:148` 搜不到结果返回 `ErrSearchNothing` 不调 next，后面所有插件被跳过；
- Gin 中间件、embedding 的装饰器洋葱，全是同一个模式。

## 3.3 黑板模式

对比"传纸条"（每步输出塞给下一步，两两耦合），**黑板**是：一块公共板，每个步骤只写自己那格、读别的格：

```
ChatManage 黑板
┌─────────────┬───────────────┬─────────────┐
│ 配置(只读)    │ 状态(可写)      │ 管道设施      │
│ 原始问题/阈值 │ RewriteQuery   │ EventBus    │
│  TopK 等     │ SearchResult   │ 消息ID       │
└─────────────┴───────────────┴─────────────┘
```

收益：新增插件零改造（取它要的、写它产的）；代价：读写关系编译器不查。出现位置：读路径 `types.ChatManage` 的三格结构（`PipelineRequest`/`PipelineState`/`PipelineContext`）。

## 3.4 发布-订阅与 EventBus

直接调用像打电话（A 必须认识 B）；**发布-订阅像广播电台**：A 对话筒喊"事件 X 发生了"，谁想听谁订阅，A 不知道有谁在听。

```
插件 ──emit(EventAgentFinalAnswer{内容:"退"})──▶ EventBus
                                                  ├─ 订阅者1：SSE handler → 浏览器
                                                  ├─ 订阅者2：落库协程
                                                  └─ 订阅者N：随时加
```

价值一个词：**解耦**。位置：`internal/event/event_bus.go`，`chat_completion_stream.go` 只管吐 token，不关心谁在听。

## 3.5 Go 并发三件套

**goroutine = 再雇一个工人**：`go searchWeb()` 并行跑，主流程不等待。

**channel = 传送带**：一个工人放货，另一个取货，没货就等（天然同步）：

```go
ch := make(chan string)
go func() { ch <- "结果" }()
result := <-ch
```

`ChatStream` 返回的 channel 就是传送带：LLM 每生成一段就放进去，消费者在另一头接。

**WaitGroup + Mutex = 点名收工 + 保险柜**（`search.go:93-120` 一模一样）：

```go
var wg sync.WaitGroup
var mu sync.Mutex
wg.Add(2)
go func() { defer wg.Done(); mu.Lock(); results = append(results, kb...); mu.Unlock() }()
go func() { defer wg.Done(); mu.Lock(); results = append(results, web...); mu.Unlock() }()
wg.Wait()
```

去掉 mutex 会发生**数据竞争**（两个工人同时写一个切片，结果丢失或崩溃）。为什么并发：知识库搜索 300ms + 联网搜索 500ms，串行 800ms，并行 500ms。

**context**：贯穿所有函数签名的"施工令"——用户关页面它就被取消，各环节听令行事。

## 3.6 SSE：水龙头模式

普通 HTTP 是**桶装水**（攒好一次给）；SSE 是**水龙头**（连接建立后一格一格持续写）：

```
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"type":"answer","content":"退"}

data: {"type":"answer","content":"款流程","done":true}
```

全链路：LLM 流式吐 token → Go channel 传送带 → EventBus 广播 → SSE handler 写帧 → 前端逐帧渲染。

## 3.7 两个设计原则

**特性开关（Feature Flag）**：流水线按配置现场拼装（`AddIf(联网开启, WEB_FETCH)`）——同一代码库不同场景跑不同流程，改配置不改代码。

**优雅降级的分级哲学**：

| 组件类型 | 失败时 | 实例 |
|---|---|---|
| 锦上添花（改写、rerank、扩展） | 降级继续 | query_understand 用原问题；rerank 用原始排序 |
| 命脉（最终生成） | 报错终止 | ChatStream 失败返回 ErrModelCall |

判断标准：**这个组件挂了，答案还"对不对" vs 还"有没有"**。
