# 第 13 章 · 模型适配层：`internal/models/`

模型层把几十家厂商的 API 收敛成几个统一接口。子目录按用途划分：

```
internal/models/chat/       LLM 对话（SSE 流式、缓存、Langfuse 包装）
internal/models/embedding/  向量化（批处理、缓存）
internal/models/rerank/     精排
internal/models/vlm/        视觉理解（文档里的图片）
internal/models/asr/        语音识别
internal/models/provider/   厂商元数据/适配（DeepSeek、Moonshot、Hunyuan…）
internal/models/limiter/    并发闸门
```

## 13.1 三个核心接口

**Chat**（`chat/chat.go:87`）：

```go
type Chat interface {
    Chat(ctx context.Context, messages []Message, opts *ChatOptions) (*types.ChatResponse, error)
    ChatStream(ctx context.Context, messages []Message, opts *ChatOptions) (<-chan types.StreamResponse, error)
    GetModelName() string
    GetModelID() string
}
```

注意 `ChatStream` 返回 **channel**——第 3 章的传送带：厂商 SDK 往里放流式片段，消费端（SSE goroutine）在另一头接。接口统一后，上层（chat_completion_stream 插件）完全不知道底下是 OpenAI 还是 Ollama。

**Embedder**（`embedding/embedder.go:16`）：`Embed`（单条）、`BatchEmbed`（批量）、`GetDimensions`（向量维度）。

**Reranker**（`rerank/reranker.go:14`）：

```go
type Reranker interface {
    Rerank(ctx context.Context, query string, documents []string) ([]RankResult, error)
}
type RankResult struct {
    Index int; Document DocumentInfo; RelevanceScore float64
}
```

`RankResult` 自定义了 `UnmarshalJSON`：先找 `relevance_score` 字段、没有就回落 `score`——**不同厂商返回字段名不一致**，适配层吸收脏活，上层只见统一结构。

## 13.2 工厂：按厂商路由

`embedding/embedder.go:110` `newEmbedder` 的大 switch：本地走 Ollama；远端先 `provider.DetectProvider(BaseURL)` 推断厂商，再路由到 Aliyun/Volcengine/Jina/Azure/Nvidia/Gemini/Zhipu/WeKnoraCloud；**default 落到 OpenAI 兼容实现**——大多数厂商都提供 OpenAI 兼容端点，所以"不认识的厂商"也有正确行为。

**厂商适配的现实复杂度**（127–173 阿里云案例）：

- 模型名带 `vision`/`multimodal` → 多模态模型，必须走 DashScope 专用 API 端点；
- 纯文本模型（text-embedding-v1/v2/v3/v4）→ 必须走 OpenAI 兼容接口，否则响应格式不匹配、返回空数组；
- 用户填了兼容模式的 URL 但选了多模态模型 → **代码自动纠正 URL**（剥掉 `/compatible-mode` 段）。

教科书上的干净抽象 ≠ 生产现实：适配层充满这种"帮用户擦屁股"的防御逻辑。

## 13.3 配置映射的单一来源

`ConfigFromModel`（embedding:66、chat.go 同名函数）把 `types.Model`（DB 里的模型配置）翻译成各层 Config。注释点明设计意图：

> 生产路径（从 DB 拉起）和测试连接路径（临时表单）**共享这份映射**，避免重复样板。

两处路径字段映射不一致是经典 bug 源（测试连接成功、正式使用失败）——单一映射函数根治。

## 13.4 装饰器洋葱（复习 + 补充）

`NewEmbedder`（89–108）：

```go
e = wrapEmbeddingConcurrency(e, config.MaxConcurrency)  // 最里层：限流闸门
if logger.LLMDebugEnabled() { e = &debugEmbedder{inner: e} }
if langfuse.GetManager().Enabled() { e = &langfuseEmbedder{inner: e} }
```

- 限流裹在**最里面**：先限流再观测，Langfuse 里的耗时指标才是真实排队后的；
- debug/langfuse 按需叠加（未开启零开销）；
- `SetSupportsDimensionOverride`（94）：接口能力探测（`interface{ Set...(bool) }` 类型断言）——不是所有实现都支持，有就设、没有跳过。

运行时想加观测？套一层即可，核心零改动。

## 13.5 模型也走插件化（新版图）

`manager.go:453` `processChatModel`：外部插件可声明 `extension_types: ["model_provider"]`（目前只支持 chat，85 行校验），把一个外部进程包装成 `chat.Chat` 接口实现——**模型本身也成了可插拔组件**。工厂注册：

```go
chat.RegisterExternalChat(modelName, func(cfg *chat.ChatConfig) (chat.Chat, error) {
    return &processChatModel{connector: connector, config: cfg}, nil
})
```

## 13.6 与增量缓存工作的关联（重点）

- **embedding 可缓存性的根基**：相同文字+相同模型=逐位相同的向量（确定性函数）。但**缓存 key 必须含模型身份**（ModelID + 维度 + 相关参数）——换模型后旧向量绝不可复用（向量空间不可通约，第 2 章）；
- **LLM 缓存的非确定性**：temperature>0 的 LLM 输出不稳定，缓存策略要么缓存确定性参数（Temp=0 的摘要/抽取），要么接受"缓存命中=旧版本输出"；
- **VLM/ASR 同理**：图片转写、音频转写按内容 hash 缓存时，key 同样要含模型身份与版本。
