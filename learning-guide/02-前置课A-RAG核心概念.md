# 第 2 章 · 前置课 A：RAG 核心概念

本章不看代码，把地基概念打牢。每个概念标注它在 WeKnora 哪里出现。

## 2.1 LLM：一台"接话机器"

**本质**：LLM 预测下一个最可能的 token，接上去，再预测下一个……循环直到生成完整回答。

由此推出三个必备概念：

- **Token（词元）**：模型处理文字的最小单位。英文约 1 词 ≈ 1.3 token，中文约 1 字 ≈ 1 token。**计费、限制都按 token 算**——WeKnora 切分器里"把 chunk 压到 token 上限 90% 以内"就是为了不超模型硬限制。
- **上下文窗口**：模型一次能"看见"的文字总量。想象一张桌子：问题和资料都摊在桌上作答。窗户可能 128K token，但知识库可能是几个 GB——**桌子永远不够大，这是 RAG 存在的根本原因**。
- **Prompt**：放进窗口的全部内容。RAG 场景的典型结构：`[系统指令] + [检索资料片段] + [用户问题]`。拼装发生在 `chat_pipeline/into_chat_message.go`，模板在 `config/prompt_templates/`。

**RAG 的本质是一道开卷考试：检索系统负责翻书找页码，LLM 负责照着答题。**

两个缩写：**VLM**（视觉语言模型）= 能看图的 LLM，用于理解文档里的图片；**ASR** = 语音转文字，处理音频文件用。

## 2.2 Embedding：把"意思"变成坐标

**问题**：计算机怎么知道"我很累"和"精疲力尽"是一个意思？字符串对比做不到。

**解法**：embedding 模型把每段文字变成数字数组（向量）：

```
"我很累"   → [0.21, -0.83, ..., 0.07]   （1024 个数）
"精疲力尽" → [0.19, -0.80, ..., 0.05]   （很接近）
"我饿了"   → [-0.65, 0.12, ..., 0.91]  （差很远）
```

训练好的模型把"意思相近的文字"映射到空间中相近的位置。语义相似度 = 向量夹角（余弦相似度，越接近 1 越像）。

三个实用认知：

1. **Embedding 模型和 LLM 是两种模型**：embedding 文字进→数字出（只会打分）；LLM 文字进→文字出。所以 `internal/models/embedding/` 和 `internal/models/chat/` 是两个目录。
2. **向量空间不可通约**：即使两个模型维度相同，坐标系含义也不同——A 模型里 (3,7) 是"疲惫"方向，B 模型里可能是"食物"方向。**换 embedding 模型必须全库重新向量化**；缓存 key 必须包含模型身份。
3. **embedding 只对短文本效果好**：整篇文档塞进去，向量被"平均稀释"——这就是为什么必须先切 chunk 再 embedding。

## 2.3 向量检索：海选机制

把用户问题也变成向量 Q，和库中每个 chunk 向量算相似度，取前 K 个（Top-K）。

工程上靠**向量数据库**的 **ANN（近似最近邻）索引**（如 HNSW 图）：查询时只探索"大概率最近"的一小片区域，牺牲一点准确率换百倍速度。

**向量检索的软肋**：懂"意思"但不懂"精确"。搜"报错 ERR-1042"，可能给一堆语义相近但没有这个错误码的内容。

**关键词检索（倒排索引）**：传统搜索技术，建"词→文档列表"的倒排表，`ERR-1042` 一字不差才命中。

**混合检索（Hybrid Search）**：向量管语义、关键词管精确，两路各取一批再融合。两路失误模式互补：

| 查询 | 向量路 | 关键词路 |
|---|---|---|
| "ERR-1042 报错怎么办" | 召回一堆"故障排查"（没命中码） | ✅ 直接命中 |
| "电脑开不了机"（文档写"设备无法启动"） | ✅ 语义命中 | 分词后一无所获 |

融合常用 **RRF（倒数排名融合）**：不比绝对分数（量纲不同），只比各自排名。

## 2.4 Rerank：复试机制

| | 双塔（Bi-encoder，embedding） | 交叉编码（Cross-encoder，rerank） |
|---|---|---|
| 工作方式 | 问题和文档**分别**变向量再比距离 | 问题和文档**拼在一起**喂模型，直接吐相关分 |
| 速度 | 快（文档向量可预计算入库） | 慢（每对现场跑一次模型） |
| 精度 | 中 | 高 |

**两阶段漏斗**（工业标配）：

```
100 万 chunk → [向量海选：ANN，毫秒级] → Top 50 → [Rerank 精排] → Top 5 → 进 prompt
```

关键认知：**不是谁更强的问题，是谁的算力结构适合哪个位置**——海选模型必须"文档侧可离线预计算"才能扛百万级；精排模型"逐对深算"只配小候选集。用 rerank 搜全库 = 现场跑 100 万次推理，不可行。

## 2.5 长上下文的陷阱

即使装得下也不该全塞：

- **成本**：按 token 计费，每次提问塞全库 = 每问一次付一次全库的钱；
- **Lost in the Middle**：塞 100 段资料，模型往往只认真看开头结尾，中间视而不见——"精选 5 段"不只是省钱，**答案质量本身更高**。

RAG 的两个战略价值：**知识可更新**（文档一换立刻生效）+ **可溯源**（答案标注出处）。

## 2.6 Chunk：检索质量的第一决定因素

切分是**两头怕**的平衡术：

- **太大** → 语义稀释，向量"哪个主题都不像"；还占窗口预算；
- **太小** → 缺主语和上下文，命中了也没法用（"它支持该功能"——"它"是谁？）。

WeKnora 的三个对应设计：**heading 切分 + 面包屑**（补"第二章 > 2.3 节"）、**父子 chunk**（检索用小块保精准、返回大块保完整）、**ValidateChunks 质检**（切坏的降级重切）。

## 2.7 两个小工程概念

- **SSE（Server-Sent Events）**：服务器向浏览器单向持续推文本的 HTTP 技术。LLM 吐一个 token 推一次 → 打字机效果。前端用 `@microsoft/fetch-event-source` 消费（`frontend/src/api/chat/streame.ts`）。
- **Query 改写**：用户原话不适合直接检索（口语化、有指代），先用 LLM"洗"成检索友好的形态。对应 `chat_pipeline/query_understand.go`。
