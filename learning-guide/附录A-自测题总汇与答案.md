# 附录 A · 自测题总汇与答案

编号规则：章-题号（如 4-2 = 第 4 章第 2 题）。

## 第 1 章 初识

**1-1 RAG 类比**：LLM 是没读过内部文档的专家；检索系统当图书管理员找资料，LLM 照资料答题。答案有出处、可溯源、可更新。

**1-2 三个心智模型**：① handler/service/repository 三层架构；② 耗时活走 asynq 异步队列（HTTP 不阻塞、可重试、可水平扩 worker）；③ 一切可插拔（向量库/模型/存储/解析器，工厂+适配器贯穿）。异步的原因：解析向量化分钟级，HTTP 不能干等；队列天然提供重试和削峰。

**1-3 Go 版**：后端全 Go（Gin+dig+asynq），仅 docreader（解析）和 mcp-server（MCP）两个 Python 边车。旧教程的 Python 目录结构已失效。

## 第 2 章 RAG 概念

**2-1 三个原因**：① 上下文窗口装不下；② 成本（按 token 计费，全库塞入=每问付全库的钱）；③ Lost in the Middle（长上下文注意力稀释，精选 5 段答案质量反而更高）。

**2-2** embedding：文字进→数字出（打分）；LLM：文字进→文字出。换 embedding 模型必须全量重算：**向量空间不可通约**——即使维度相同，坐标系含义也是两套（A 的 (3,7) 是"疲惫"，B 的可能是"食物"）。缓存 key 必须含模型身份。

**2-3** rerank 让最终进 prompt 的 5 段排序更准。不能用它搜全库：cross-encoder 逐对评分，100 万 chunk = 现场跑 100 万次推理；而 bi-encoder 的文档向量可离线预计算 + ANN 索引只探索小片区域。**是算力结构决定位置，不是强弱**。

**2-4** 向量路懂语义不懂精确（"ERR-1042"→召回"故障排查"）；关键词路精确不懂语义（"电脑开不了机" vs 文档"设备无法启动"→落空）。互补 → 混合检索 + RRF 融合（比排名不比分数）。

**2-5** chunk 是检索最小单位：太大→语义稀释+占窗口；太小→缺主语缺上下文（"它支持该功能"——"它"是谁？）。切分是两头怕的平衡术。

## 第 3 章 工程模式

**3-1** 闭包组装洋葱必须从最里层开始（穿衣服从里往外）：想包住别人得先有别人。从尾往前循环，每个插件捕获"链条剩余部分"作 next。

**3-2** `upperCase` 不调 next 直接 return：日志前半句照常打，**"最终处理"和"处理完毕"都不出现**——短路了，内核及之后的层全部不执行。

**3-3** 数据竞争：两个 goroutine 同时 append 同一切片 → 结果丢失、崩溃等未定义行为。Mutex 保证写互斥。

**3-4** rerank 失败会直接报错终止 → 每逢 rerank 服务抖动，用户就看到失败页面；正确行为是降级用原始排序，答案"糙一点但总有"。增强组件挂了答案变糙；命脉挂了答案消失——分级处理。

## 第 4 章 写路径

**4-1** 文件和数据库记录都已安全落地，任务只是没排上队——标记 enqueue_failed，数据不丢、可手动重触发。返回成功 + 状态字段比让用户重传 200MB 体验好。取舍：数据完整性 > 流程完整性。

**4-2** 防队列"至少投递一次"语义下的重复消费（幂等：completed 直接返回）和重复执行（deleting/cancelled 退出）。竞态补丁：用户在"入口检查"和"写 processing"之间点取消 → 不复查会把 cancelled 覆盖回 processing，下游检查点全乱。

**4-3** "检索粒度 vs 上下文完整性"的矛盾。检索用**小**子块（向量精准），命中后换**大**父块喂 LLM（上下文完整）。

**4-4** 开头插入 → 后面所有 chunk 的 index 偏移 → hash 里掺了 index → 全部判为变更 → 全量重算。尾部追加前面的 index 不动、缓存全命中。本质是"锚定序号"的 diff；改进方向：按纯内容 hash 对齐（LCS 式），允许错位。

**4-5** 限流在最里层：先限流再计时/上报，观测指标才是真实排队后的耗时；观测在外还能覆盖"被限流拒绝"的情况。

## 第 5 章 读路径

**5-1** 见 3-1。

**5-2** search 之后全部被跳过：rerank、merge、filter_top_k、into_chat_message、chat_completion_stream。用户看到兜底回复（FallbackStrategy/FallbackResponse 配置，如固定话术），而不是报错。

**5-3** 答案失去精排：排序退回检索原始分，Top-5 里可能混入弱相关片段，答案质量变糙但仍有引用有内容——系统"看起来正常"因为降级是静默的（只有 Warn 日志和 Langfuse span 标记）。这就是优雅降级的代价：**质量损失不可见，需要监控发现**。

**5-4** Request（只读配置：问题、阈值）、State（可写状态：改写后问题、检索结果）、Context（设施：EventBus、消息 ID）。收益：新插件零改造；代价：读写关系编译器不查，靠约定。

**5-5** 以前引用在流水线返回后发——那时 complete 事件已关 SSE，前端只能刷新才见引用。现在开流前发，浏览器收流期间就能渲染引用区。

## 第 6 章 骨架

**6-1** Shutdown 优雅：停止接新请求、等在途请求完成（可配超时）后退出；Close 立即断所有连接。排水用 Shutdown（不杀无辜请求）；用户第二次按信号说明等不及了，用 Close 强杀。滚动部署时先关 listener 让下一进程马上绑端口。

**6-2** Auth 在 Logger 外时：Logger 看不到认证结果，**所有请求（含 401）都被记录耗时**——审计友好；反过来 401 请求将不被访问日志覆盖。

**6-3** 过期路由模板的症状是"所有 API Key 在该路由静默 403"——运行时发现需要用户报障 + 查日志；启动时 panic 把发现成本降到部署时刻（fail fast：错误越早暴露越便宜）。

**6-4** 防管理员在 UI 被撤销后，下次重启被环境变量"复活"。设计意图：变量只在"系统中还没有任何管理员"的冷启动窗口授予权力。

**6-5** 标记结构体由 dig 认领：NewRouter 一个参数收下 40+ 个依赖字段，dig 按类型逐个从容器注入。

## 第 7 章 插件框架

**7-1** 扩展点要窄：插件越笨系统越稳。切分/向量化/入库留在主流程——第三方代码崩溃/作恶/版本腐烂的影响面被窄缝挡住。宽接口 = 平台之癌（无限兼容债）。

**7-2** 业务失败是"结果"不是"事故"（主机可 fallback 到别的解析器）；且 gRPC status error 在 stdio/跨语言场景处理麻烦。原则：**传输错误走 error 通道，业务结果用数据结构**。

**7-3** ProcessDocument 依赖的只是 DocReader 抽象——插件对流水线是"碰巧活在另一个进程里的普通解析器"，主流程零改动（依赖倒置）。去掉皮则 convert() 要感知 gRPC/进程生命周期，核心代码被污染。

**7-4** `--rm`：容器退出自动清理不留尸体；纳秒时间戳：插件崩溃重启时新旧容器不同名，不会撞名冲突。

**7-5** 本机 TCP。约定：主机向 `127.0.0.1:0` 申请临时端口拿到地址 → 关闭监听 → 通过环境变量 `WEKNORA_PLUGIN_ADDR` 告诉插件 → 插件绑定该地址。缺陷：关闭与绑定之间有极小竞争窗口（端口可能被抢）；限定 loopback 且存活几秒，风险可接受。

**7-6** 防插件与主机协议不匹配（主机升级改了协议）。在第三幕握手时失败：GetManifest 返回的 ProtocolVersion ≠ 主机的 → 拒绝加载。宁可拒绝也不静默错位（字段对不上时的行为不可预测）。

**7-7** datasource 是最后注册的，失败要逆序撤销之前的全部：parser → model → web_search，然后 Close。

## 第 8 章 安全

**8-1** 普通宿主进程无法如实承诺不发出站 socket——承诺无法由能力兑现。docker 的 `--network none` 是内核级断网，能兑现。loader 拒绝假的承诺组合。

**8-2** 非 root/只读 FS/无 capabilities/禁提权/进程上限/断网/只读挂载——分别防 root 逃逸、篡改持久化、基础能力滥用、setuid 提权、fork 炸弹、外传与 SSRF、写白名单外。纵深防御：攻击者要同时穿透全部七层才能得手，单层失守不致命。

**8-3** docker socket = Docker daemon API = 可起任意容器、挂载宿主任意路径 = root 等价。只有 app 容器持有（为了拉起插件容器）；插件容器**永远不持有**（socket 不传入）。

**8-4** IsDeleted=true 是插件对"源头事实"的感知上报；deletion_policy 是主机的决策动作（retain 保留 / delete 走正常删除流程）。感知在外、决策在内——插件永不直接碰主机数据。

**8-5** 人眼 review 会漏、会随时间遗忘；自动化断言（network-probe 实验 + 命令无端口的测试）把安全不变量固化到 CI——将来任何人改代码破坏约束，机器当场拦截。

## 第 9 章 集成与同步

**9-1** 获得依赖倒置：核心只见 DocReader 抽象，插件实现可热插；直接传 PluginClient 则 convert() 要感知 RPC、重连、序列化——跨进程细节污染核心。

**9-2** 状态归插件所有：主机不理解、不修改、只透传。主机不需要跟随插件 cursor 格式演化；插件可以随意改内部结构不破坏兼容。

**9-3** 换来实现简单、跨平台一致（不依赖 inode/文件 ID）。问题：重命名文件的旧知识被删重建（增量变全量）；无法区分"重命名"和"删除+新增"的语义差异。

**9-4** retain：保留知识、完成同步、不删派生数据（安全默认——删错代价远大于留错）；delete：走主机正常删除（chunk/向量/文件/图/软删）。默认 retain 是"宁可冗余不可误删"。

**9-5** 同步失败说明"这次看到的世界"不可信；保留旧状态 = 最后一次已知的完整一致状态。半成品状态（部分新部分旧）才是最难恢复的。

## 第 10 章 测试与发布

**10-1** 协议层（stdio 回环：JSON codec/方法路由正确）、安全层（docker 命令无端口：断网承诺不被回退）、业务层（增量只含变化文件）。安全约束单测因为它"平时看不见、坏了才致命"，且最容易被无意的重构破坏。

**10-2** pkg/ 对外（稳定契约）、internal/ 编译器强制私有。契约是负债：每次改动都要求所有现存插件兼容或升级 protocol_version，成本永久存在。

**10-3** 独立 go.mod 让插件作者的构建不依赖 WeKnora 源码树（只依赖发布的 SDK 版本）；"不含指向 checkout 的路径"防脚手架把插件作者绑架到 WeKnora 仓库结构上。

**10-4** 旧插件在握手（GetManifest 对比 ProtocolVersion）时被拒绝加载，日志明确报"protocol mismatch"。比静默错位好：静默错位 = 字段对不上，行为不可预测、难以排查；显式失败 = 立即可定位。

## 第 11 章 Agent

**11-1** 控制流移交：流水线由代码定序，Agent 由 LLM 现场决定调什么工具、传什么参、何时收手。代码定围栏：MaxIterations、工具白名单、schema 校验、卡死检测；LLM 做选择：选哪个工具、参数内容、是否继续。

**11-2** 工具描述是模型选工具的唯一依据。写"不要用我做什么"：① 防错选（语义搜索找错误码 → 整轮作废）；② 整形参数（禁止贴原文）；③ 划清重叠工具的边界防来回乱试。描述质量决定 ReAct 轮数。

**11-3** 检测模型连续输出相同内容 = 陷入死循环。双保险：硬上限（MaxIterations）防一切失控但浪费轮次；软检测早停省轮次。LLM 会抽风，代码必须设围栏。

**11-4** 用已有工具结果合成答案再退出（抢救，不丢弃已花的成本）；取消后跳过兜底生成——否则兜底 LLM 调用在已取消的 ctx 上失败，把通用"抱歉"泄漏给用户主动放弃的对话。

## 第 12 章 Graph RAG

**12-1** 多跳关系信息分散在多个 chunk（Docker 的段、K8s 的段），没有任何单段同时讲两者关系；向量逐段打分，永远拼不出"关系"。

**12-2** 多节点 → 图谱碎裂："K8s 依赖 Docker"的边只挂一个 Docker 节点，其余成孤岛，查 Docker 邻域看运气漏边。单节点 + ChunkIDs 列表：关系全汇聚（不丢）+ 出处可溯（跳回原文）。

**12-3** ① 图互联 + 权重/度是全文档统计量，动一处牵全身（向量按 chunk 孤立，可单块修）；② LLM 抽取非确定性，没变的 chunk 重抽也可能漂移，增量 patch 制造不一致；③ 增量维护需跨版本实体对齐（entity resolution 难题），做错比不做糟。重建 = 花钱买一致性。

**12-4** 缓存/增量成立的前提是确定性（同输入同输出）。LLM 抽取同段文字两次可能给出不同实体名/关系——"旧图谱里的 Docker"和"这次抽出的容器技术"无法机械判定为同一节点，diff 的基础塌了。

**12-5** Agent 工具（query_knowledge_graph：关系探索、网络分析）；流水线实体检索（extract_entity → 查实体邻域 chunk 补进检索结果）。

## 第 13-15 章 支撑层

**13-1** Chat：消息进→回答出/流 channel；Embedder：文本→向量；Reranker：query+docs→相关分。ChatStream 返回 channel：厂商流式片段由 SDK goroutine 放入传送带，消费端在另一头接——生产者消费者解耦。

**13-2** 大多数厂商提供 OpenAI 兼容端点，default 落到兼容实现意味着"不认识的厂商"也有正确行为——扩展无需改代码。

**13-3** 生产路径（DB 拉起）与测试连接（表单临时拉起）字段映射不一致的经典 bug（测试通过、正式失败）。单一映射函数 = 单一事实来源。

**13-4** 先限流再观测：Langfuse 记录的耗时才是真实排队后的；顺序反了观测到的"成功"会掩盖限流拒绝。

**13-5** ModelID + 模型参数（维度等）+ 内容 hash。因为向量空间不可通约：不同模型的向量不可比、不可混存。

**14-1** 引擎（存哪）与检索方法（怎么查）正交：pgvector 可同时跑 vector（pgvector 索引）和 keywords（ParadeDB）两路；ES 天生如此。

**14-2** `internal/application/repository/retriever/` 新增包实现统一接口 + `engine_factory.go` 加 case + 引擎类型常量。上层零改动。

**14-3** merge_expand.go 的邻居扩展（短块 <350 字时顺链捞前后块拼到 850 字）。

**14-4** 两路分数量纲不同（余弦相似度 vs BM25 分），直接比无意义；RRF 按各自排名融合。

**15-1** 原生 EventSource 只支持 GET、不能带 Authorization 头；聊天接口是 POST + 认证。

**15-2** 另发一条取消 HTTP 请求 → 后端 ctx 取消 → agent/流水线的 ctx.Done() 分支（抢救答案）→ SSE 流终止。两条独立 HTTP 请求配合。

**15-3** 后端特意在开流前发引用事件——以前发在流水线返回后，complete 已关 SSE，前端要刷新才见引用（bug 疤痕）。

**15-4** 后端 handler/service/repository 分层 ↔ 前端组件/api 模块/axios 实例——"组件不直接写 URL"镜像"handler 不写业务"。
