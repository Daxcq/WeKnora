# 第 8 章 · 插件化：安全沙箱与防御纵深

插件化里**唯一不能出错**的部分。核心思想一句话：

> **承诺必须由能力兑现，不能由自觉兑现。**

## 8.1 能力即承诺

manifest 里 `permissions.allow_network: false` 不是元数据，是安全要求。文档（plugin-framework.md:67）写得很直白：

> 普通宿主进程**无法如实承诺**自己不创建出站 socket，所以 loader 直接拒绝"process runtime + 断网声明"的组合。

代码落地在 `manager.go:347`：

```go
if manifest.Runtime.Type == "process" && !manifest.Permissions.AllowNetwork {
    return nil, fmt.Errorf("plugin %q requests network isolation but process runtime cannot enforce it; use docker runtime", ...)
}
```

宁可报错，不给假保证。对比：docker runtime 能兑现，因为内核级 `--network none` 物理断网。

## 8.2 七层防御纵深（复习 + 展开）

`newDockerCommand`（manager.go:701–722）的每一层独立起作用，单层被绕过不致命：

| 层 | 参数 | 防什么 |
|---|---|---|
| 1 非 root | `--user 65532:65532` | 拿到 root 等于拿到底层一切 |
| 2 只读 FS | `--read-only` | 篡改自身代码 / 写恶意持久化文件 |
| 3 无 capabilities | `--cap-drop ALL` | 连改进程属性、绑低端口等基础能力都没有 |
| 4 禁提权 | `--security-opt no-new-privileges` | setuid/sudo 逃逸路径封死 |
| 5 进程上限 | `--pids-limit 128` | fork 炸弹拖垮宿主 |
| 6 断网 | `--network none` | 数据外传、SSRF、C2 回连 |
| 7 只读挂载 | `--mount ...,readonly` | 只能读白名单目录，不能写回 |

配套：容器 `--rm`（退出即清理）+ 名字带纳秒时间戳（崩溃重启不撞名）+ `--pids-limit`。

## 8.3 stdio 传输：为断网而生

`--network none` 后控制通道怎么办？答案：**gRPC 走 stdin/stdout**。

- 主机侧：容器 StdinPipe/StdoutPipe → `stdioConn`（manager.go:731）→ `WithContextDialer` 注入给 gRPC；
- 插件侧：`WEKNORA_PLUGIN_STDIO=1`（由 `newDockerCommand:709` 注入）→ `newStdioListener`（pluginapi:263）把 stdin/stdout 伪装成 `net.Listener`。

想绕过去访问外网？**内核层面就没有网络接口**，想违规都做不到——这就是"由能力兑现的承诺"。

## 8.4 文件系统的最小权限

`permissions.read_paths` 白名单 → 每个路径只读挂载到容器内 `/weknora/inputs/<index>`（manager.go:710–715）：

```go
args = append(args, "--mount", fmt.Sprintf("type=bind,src=%s,dst=/weknora/inputs/%d,readonly", path, i))
```

三个要点：

1. 非绝对路径会拼到插件目录下（防路径逃逸）；
2. `isHostAbsolutePath`（724）还处理了 Windows 盘符（`D:\...`）——Docker Desktop 要求挂载主机共享路径；
3. 插件配置必须用**容器内路径**（`/weknora/inputs/0`），主机路径对插件不可见——路径语义隔离。

## 8.5 信任边界：docker socket

文档 79–85 行（你的 commit `b4c57b38`）诚实标注了方案的信任前提：

> app 容器需要挂载 `/var/run/docker.sock` 才能拉起插件容器。**拿到 docker socket ≈ 拿到宿主机 Docker daemon = root 级权限**，即使 bind mount 标了 read-only。只对可信 WeKnora 部署启用此模式。

要点：socket 不给插件容器，只给 app；但 app 拿到 socket 本身就是重特权。**成熟框架文档会诚实标注自己方案的信任前提**，而不是装作没有代价。

## 8.6 插件只报告事实，主机独占决策

数据安全边界（plugin-framework.md:188–199）：

- 插件进程崩溃 → 本次同步失败，**旧知识和旧 cursor 原样保留**（主机从不让插件碰数据库）；
- 插件发现远端删除 → 上报 `FetchedItem{IsDeleted: true}` 这个**事实**；
- 删不删由主机配置决定：`sync_deletions=false` 忽略；开启后 `deletion_policy` 控制——`retain`（默认，保留知识完成同步）/ `delete`（走 WeKnora 正常删除流程：chunk、向量、文件、图数据、软删 knowledge 行）。

文档原话：*"The connector only reports the change; it never deletes host data itself."*

这是插件安全模型的**权责分离**：感知在外（插件看见远端变化），决策在内（主机决定动作）。类比：哨兵发现敌情只能上报，开火的扳机在指挥官手里。

## 8.7 验证：用实验兑现承诺

`examples/plugins/network-probe` 是安全验证教材——插件**故意**请求 `https://example.com`：

```powershell
docker build -t weknora-plugin-network-probe:dev examples/plugins/network-probe
docker run --rm --network none -e WEKNORA_NETWORK_PROBE_SELF_TEST=1 weknora-plugin-network-probe:dev
go test ./internal/datasource/plugin -run TestNewDockerCommandEnforcesManifestNetworkPolicy
```

预期：同步失败、日志同时出现被拦请求和插件 ID。配套测试断言生成的 docker 命令**没有发布任何端口**——安全约束落成自动化断言，不靠人眼。

**动手必做**：跑一遍 network-probe，亲眼看拦截日志。
