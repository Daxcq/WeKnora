# 第 5 章 · 读路径：一次提问的旅程

## 全景图

```
POST /api/v1/sessions/knowledge-chat/:session_id
  ↓
① handler/session/qa.go:724     守门：解析请求、创建消息、开 SSE
  ↓
② session_knowledge_qa.go:23    总指挥：装配 ChatManage 黑板 + 动态拼流水线
  ↓
③ KnowledgeQAByEvent (:658)     引擎：按序触发事件，逐阶段执行
  ↓
④ 插件链：query_understand → search → rerank → merge → filter_top_k
          → into_chat_message → chat_completion_stream
  ↓
⑤ EventBus → SSE               token 一个个推到浏览器
```

## 站 1：HTTP 入口——同步边界拦异步错误

`qa.go:724` `KnowledgeQA` 只有 10 行。看点在 `AgentQA`（749 行）的防御（776–783）：agent 模式开着但 agent_id 解析不到时，**在门口直接 400**。注释解释：不拦的话错误沉到异步 goroutine 深处，用户只看到断掉的流（常见成因：localStorage 残留过期 agent 选择）。

> 工程习惯：**异步系统的错误尽量在同步边界拦截**——流开出去后错误很难体面传达。

## 站 2：总指挥——黑板 + 动态拼装

`session_knowledge_qa.go:23` `KnowledgeQA`，两个核心发现：

**① `ChatManage` 是公共黑板**（105–150），三格：

- `PipelineRequest`——只读配置：问题原文、阈值（`VectorThreshold`/`RerankTopK`…来自 config.yaml Conversation 段）；
- `PipelineState`——可变状态：`RewriteQuery`、`SearchResult`…每个插件写产出、下游读；
- `PipelineContext`——管道设施：EventBus（SSE 出口）、消息 ID。

黑板模式：牺牲编译期检查，换**新增插件零改造成本**。

**② 流水线动态拼装**（164–198）：

```go
pipeline = types.NewPipelineBuilder().
    AddIf(hasHistory, types.LOAD_HISTORY).
    Add(types.QUERY_UNDERSTAND).
    Add(types.CHUNK_SEARCH_PARALLEL).
    Add(types.CHUNK_RERANK).
    AddIf(req.WebSearchEnabled, types.WEB_FETCH).
    Add(types.CHUNK_MERGE).
    Add(types.FILTER_TOP_K).
    AddIf(chatManage.DataAnalysisEnabled, types.DATA_ANALYSIS).
    Add(types.INTO_CHAT_MESSAGE).
    Add(types.CHAT_COMPLETION_STREAM).
    Build()
```

161 行：`needsRAG := hasKB || req.WebSearchEnabled`——**纯闲聊不走检索**，流水线只剩历史+生成两站，又快又省。

## 站 3：引擎——140 行的责任链

`chat_pipeline/chat_pipeline.go`：

- **洋葱反向组装**（54–68）：`for i := len(plugins)-1; i>=0; i--`——从尾往前包装，每个插件的 `next` 就是"链条剩余部分"；调 `next()` 放行，不调就短路；
- **两层结构**：外层 `KnowledgeQAByEvent`（session_knowledge_qa.go:658）按序 `Trigger` 事件类型；内层每个事件下挂插件洋葱链。"事件→插件链"的间接层是扩展点（同阶段可叠多个处理器）；
- 循环体的生产细节：每阶段包 Langfuse span（让向量库搜索/合并/拼 prompt 这些"非 LLM 工作"在追踪时间线上可见）；引用事件在开流**之前**发（以前发在流水线返回后，complete 已关 SSE，前端要刷新才见引用——bug 疤痕）。

## 站 4：插件巡礼

**`query_understand.go:58`——洗问题，三种产出**：一次轻量 LLM 调用（MaxTokens 150、Temp 0.3、关思考），产出改写问题（"它呢？"→"退款政策呢？"）、图片描述（VLM）、意图（144 `NeedsRetrieval()`——闲聊跳过检索）。失败策略（127–132）：改写失败**用原问题继续**——改写是锦上添花。

**`search.go:62`——混合检索 + 三重去重**：两个 goroutine 并发跑 KB 检索和联网搜索（93–120，WaitGroup+Mutex 模式）。亮点：召回不足自动扩展搜索补货（127）；空结果短路 `ErrSearchNothing`（148）；三层去重——chunk ID、内容签名（169）、部分包含（199 起：短块 85%+ token 出现在高分长块里判冗余）。

**`rerank.go:38`——两套优雅降级**：先"富化"候选（`getEnrichedPassage`：标题+面包屑拼进 passage）；然后 ① 阈值降级（148–163：高于阈值一个没有 → 阈值×0.7 重试，下限 0.3）；② API 失败降级（130–144：直接用检索原始排序继续）。**增强组件失败只降级不终止；核心组件失败才报错。**

**`merge_expand.go:11`——给太短的命中找邻居**：命中 <350 字的 chunk 时，顺 `PreChunkID`/`NextChunkID` 捞前后邻居拼到 850 字。写入时用父子块预防、读取时用邻居扩展治疗——双保险。

**`into_chat_message.go:33`——摆桌时刻**：片段包进 `<context id="n">` 标签（给 LLM 的资料分格，引用编号的锚点），灌进 `ContextTemplate` 的 `{{contexts}}`/`{{query}}` 占位符。FAQ 优先有专属车道（135–154：高置信 FAQ 标 `match="exact"` 排最前）。71 行又验一次输入——纵深防御。

**`chat_completion_stream.go:39`——吐字与分流**：`ChatStream` 返回 channel，goroutine 消费并发 EventBus 事件；一个流分两路——`reasoning_content` → `EventAgentThought`（思考区），正文 → `EventAgentFinalAnswer`（答案区）。`flushDecoders`（137）冲刷跨 chunk 被切断的引用标记，防"在途引用被静默丢弃"。

## 站 5：EventBus → 打字机

插件发 `types.Event` → `internal/handler/session/stream.go` 转 SSE 帧 → 前端 `@microsoft/fetch-event-source` 逐帧收 → Vue 渲染。"正在检索知识库"转圈、引用列表先出现、思考折叠、答案逐字流出——每个 UI 现象对应一个事件类型。

## 设计原则小结

1. 黑板 + 动态拼装的责任链；
2. 增强组件降级、核心组件致命；
3. 异步错误在同步边界拦截；
4. 观测埋进每个阶段（span），bug 疤痕写进注释。
