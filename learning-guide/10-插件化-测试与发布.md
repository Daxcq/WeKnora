# 第 10 章 · 插件化：测试与发布

## 10.1 三类自动化测试（都在仓库里，直接跑）

### ① stdio 回环测试（协议层）

```powershell
go test ./pkg/pluginapi -run TestDockerStdioRoundTrip
```

不起 docker，直接验证"客户端 ↔ 服务端在 stdio 上跑通 RPC"的骨架——`pluginapi` 包内自建客户端和服务器、用管道互连。它锁住的是**契约本身**：JSON codec、方法路由、stdio 监听器都正确。

### ② 主机命令构造测试（安全层）

```powershell
go test ./internal/datasource/plugin -run TestNewDockerCommandEnforcesManifestNetworkPolicy
```

断言 `newDockerCommand` 生成的命令**没有发布端口**（`--network none` 且无 `-p`）。意义：把"断网承诺"从文档变成**自动化断言**——将来有人改 newDockerCommand 加了个 `-p`，CI 直接红。安全约束必须落成测试，不靠 code review 人眼。

### ③ 增量语义测试（业务层）

```powershell
cd examples/plugins/local-files
go test .
```

造 `a.md` 和 `c.md`、只改 `c.md`、断言增量响应**只含 `c.md`**。另有墓碑测试覆盖 `IsDeleted=true`。

**三层测试各自锁住一层**：协议正确性、安全不变量、业务语义——改任何一层都有对应的网兜着。

## 10.2 发布形态

### pkg/ vs internal/ 的契约纪律

Go 模块的目录语义：

- `internal/`——**编译器强制**不可被外部 import（"核心团队内部事"）；
- `pkg/pluginapi/`——**对外发布的稳定契约**（"这是给你的"）。

推论：改 `pkg/pluginapi` 里的任何结构体字段、RPC 签名，都是**破坏性变更**，要按契约变更对待（升 `protocol_version`、考虑旧插件兼容）。这就是为什么文档说"先只外化数据源和解析器，embedding/检索继续用进程内 registry"——**契约一旦发布就是永久负债，每个扩展点外化前都要掂量兼容成本**。

### 插件是独立模块

`examples/plugins/plain-text-parser/go.mod` 是独立 module，依赖通过 fork replace 指向发布的 WeKnora SDK 版本——**不含指向本 checkout 的路径**，保证插件作者拿到的脚手架开箱即用。`examples/plugins/template` 是官方脚手架：复制、把 `replace-me` 换掉、实现 5 个 `pluginapi.Connector` 方法即可。

### 部署形态

- 镜像已就绪时：只拷 manifest 到 `WEKNORA_PLUGIN_DIR` 的子目录，重启后看日志 `external datasource plugin loaded`；
- compose 部署：设 `WEKNORA_PLUGIN_HOST_DIR`（主机目录，一插件一子目录），compose 挂载到 `/plugins` 并自动设 `WEKNORA_PLUGIN_DIR`；app 容器带 Docker CLI + socket 挂载（Docker 型插件需要）；
- process 型插件：可执行文件必须放进挂载目录，command 用容器内路径（如 `/plugins/local-files/local-files`）。**process 无隔离**——文档明说"用 Docker runtime 来跑声明了 allow_network:false 的插件"。

## 10.3 动手：从零写一个插件（毕业实操）

目标：CSV 解析插件（CSV → Markdown 表格）。

1. `cp -r examples/plugins/template my-csv-parser`（或参考 plain-text-parser）；
2. 实现 `Parser`：

```go
func (p parser) Parse(_ context.Context, req *pluginapi.ParseRequest) (*pluginapi.ParseResponse, error) {
    if !strings.HasSuffix(strings.ToLower(req.FileName), ".csv") {
        return nil, fmt.Errorf("unsupported: %s", req.FileName)
    }
    // 解析 CSV → 生成 | a | b | 形式的 Markdown 表格
    return &pluginapi.ParseResponse{MarkdownContent: md, Metadata: map[string]string{"parser": "my-csv-parser"}}, nil
}
```

3. manifest：`extension_types: ["document_parser"]`、`file_types: ["csv"]`、`weknora_version` 填当前版本区间、`permissions.allow_network: false`、`runtime: docker`；
4. `go test ./...` → `docker build -t my-csv-parser:dev .` → manifest 拷进插件目录 → 重启 WeKnora；
5. 验证：上传一个 CSV，确认走你的插件（看 Metadata 或日志）。

**进阶**：给插件加一个单元测试锁住"非 CSV 返回错误"的边界——参考 plain-text-parser 的 `main_test.go`。

## 10.4 毕业标准

能做到以下三条，插件化板块毕业：

1. 能给别人讲清"为什么 `--network none` 的容器还能跑 gRPC"（第 7 章 stdio 注入）；
2. 能从空目录写出一个能被 WeKnora 加载的插件（本章实操）；
3. 能说出改 `ParseRequest` 字段会破坏什么、需要什么迁移策略（protocol_version 升级 + 旧插件握手失败被拒——宁可拒绝也不静默错位）。
