# 第 4 章 · 写路径：一份 PDF 的旅程

## 全景图

```
[上传] handler/knowledge.go:316        ← 站1：验权限、验文件
   ↓
[入库+投递] service/knowledge_create.go:25 ← 站2：存文件、建记录、丢进 Redis 队列
   ↓  (HTTP 请求到此结束，立刻返回)
[worker] service/knowledge_process.go:3147 ProcessDocument ← 站3：解析、状态机
   ↓
[切分] infrastructure/chunker/strategy.go ← 站4：三级切分链
   ↓
[向量化+入库] knowledge_process.go:267 processChunks ← 站5：embedding → 向量库
```

**最关键的认知**：站 2 结束时 HTTP 就返回了（前端马上看到"处理中"），重活全在后台 worker 里做。**异步边界**画在"入库"和"处理"之间。

## 站 1：HTTP 入口——只做守门员

`internal/handler/knowledge.go:316` `CreateKnowledgeFromFile`，四件事：

1. **权限校验**（321–332）：Admin/Editor 才能传；把 `effectiveTenantID` 塞进 context——**多租户隔离从这开始**；
2. **取文件验大小**（335–352）：默认 50MB，读 `MAX_FILE_SIZE_MB`。注释解释了为什么不做成 UI 开关：nginx/docreader/浏览器都在启动时缓存该值，做成运行时可调会悄悄不一致——**一致性优先于灵活性**；
3. **解析表单附加项**（367–411）：metadata、多模态开关、`process_config` 覆盖（本次上传临时覆盖库默认配置）、标签；
4. **调 service 回 JSON**。

> 分层要点：handler 不写业务、不碰库，只把"HTTP 世界翻译成 Go 世界"。

## 站 2：Service 入库——异步边界的这一侧

`knowledge_create.go:25`，按序五步：

**① 快速失败**（40–69）：视频拒、FAQ 库拒文件上传、存储没配好拒、类型不合法拒。越早拒绝越省成本。

**② 内容寻址去重**（71–101）：算文件 hash，同租户同库下同 hash 同大小 → 更新旧记录时间、返回"重复文件"标记（不是报错）。

**③ 配额与安全**（103–126）：存储配额；`secutils.ValidateInput` 防文件名注入。

**④ 落两处持久化，顺序有讲究**（161–179）：先存对象存储（`resolveFileService` 工厂按库配置选 local/minio/s3/cos…），再写库；**写库失败回手删文件**（不留孤儿）。初始状态 `ParseStatus: "pending"`、`EnableStatus: "disabled"`——先视为不可用，避免半成品被检索到。

**⑤ 投递异步任务**（186–252）：

```go
task := asynq.NewTask(types.TypeDocumentProcess, payloadBytes,
    documentProcessTaskOptions(s.config, asynq.MaxRetry(3))...)
info, err := s.task.Enqueue(task)
```

payload 只装 worker 需要的最小信息。**入队失败不报错**（220/238 行）：文件和记录已落地，只标记 `enqueue_failed`——数据不丢、任务可重触发，好过让用户重传 200MB。

> **asynq**：基于 Redis 的 Go 分布式任务队列。`MaxRetry(3)` 自动重试；worker 可用 `asynq.GetRetryCount(ctx)` 知道第几次重试。

## 站 3：Worker 主流程——状态机 + 防御性设计

`knowledge_process.go:3147` `ProcessDocument`，前 100 行是分布式任务防御的范本：

- **幂等检查**（3177–3220）：`deleting`/`cancelled` 退出；`completed` 直接返回——队列"至少投递一次"的语义要求消费端幂等；
- **竞态补丁**（3236–3248）：翻 `processing` 前**再查一次**中止状态——防用户在两次检查之间点取消，worker 把 cancelled 覆盖回 processing。真实生产 bug 的疤痕；
- **媒体早期分流**（3264–3295）：图片没开多模态失败、音频没配 ASR 失败、视频永久不支持——又是 fail fast；
- **三种来源汇流**（3301 起）：FileURL（SSRF 复检→下载→落存储）/ URL（抓网页补标题）/ Passages（纯文本直接构造 chunk）/ 文件 → 都走 `s.convert()`。

**convert 之后的增强**（3420–3501）：音频 ASR 转写（结果替换 `MarkdownContent`）；图片转存对象存储、markdown 引用改新地址（远程 http 图也下载转存，防外链失效）。

**到这一步，无论来源是什么，手里只剩一份 Markdown**——前端多样、后端归一。

> **SSRF**（3303 `ValidateURLForSSRF`）：服务端替用户请求 URL 时，防用户塞 `http://169.254.169.254/`（云元数据接口）或内网地址。校验 + 防 DNS 重绑定是标准组合。

## 站 4：切分——三级策略链 + 质检兜底

`internal/infrastructure/chunker/strategy.go`。核心循环：

```go
for i, tier := range chain {
    out := runTier(tier, text, cfg, profile)
    if v := ValidateChunks(out, totalChars, cfg.ChunkSize); v.OK {
        return out          // 这个层级切得好，用它
    }                        // 否则降级
}
```

- **Tier 1 heading**：有清晰标题时按标题切，每个 chunk 带 `ContextHeader` 面包屑（`第二章 > 2.3 节`）；
- **Tier 2 heuristic**：无标题文档用启发式；
- **Tier 3 legacy**：递归字符切分，永远可用的保底；
- **质检**：覆盖率、块大小分布不合格就降级——**切分器不信任自己**。

两个进阶设计：

1. **父子 chunk**（`SplitParentChild:135`）：检索用**小**子块（向量精准），命中后返回**大**父块（上下文完整）——"检索粒度 vs 上下文完整性"矛盾的标准解法（parent-child retrieval）。`mergeBreadcrumbs:175` 去重父子重复面包屑；
2. **token 上限自适应**（`ensureDefaults:248`）：配置了 TokenLimit 时按语言把字符预算压到上限 90% 内（中文 1 字≈1 token、英文 1 词≈1.3 token，换算分语言）。

## 站 5：向量化与入库——洋葱圈与增量 diff

`knowledge_process.go:267` `processChunks`。

**① Embedder 是洋葱**（`internal/models/embedding/embedder.go:89`）：

```go
e = wrapEmbeddingConcurrency(e, config.MaxConcurrency)  // 最里层：限流
if logger.LLMDebugEnabled() { e = &debugEmbedder{inner: e} }
if langfuse.GetManager().Enabled() { e = &langfuseEmbedder{inner: e} }
```

厂商适配器被一层层装饰器裹住：限流在最里（先限流再观测，指标才真实）。`newEmbedder:110` 的大 switch 展示厂商适配的现实复杂度（阿里云 vision 模型走 DashScope 专用端点、URL 填错自动纠正）。

**② 增量重解析 diff**（298–364）：

```go
h := ComputeContentHash(knowledge.ID, idx, chunkData.Content)
if oldHash, exists := oldHashByIndex[idx]; exists && oldHash == h {
    unchangedCount++; unchangedIndexSet[idx] = true   // 没变 → 复用
}
```

只删内容变了的 chunk 向量（347 `DeleteByChunkIDList`），没变的复用旧向量旧摘要。没有它，改一个错别字 = 全文所有 chunk 重算 embedding + 重生成摘要。

**已知局限**：hash 把 `chunkIndex` 也掺进去了（`ComputeContentHash(knowledge.ID, idx, content)`）。**开头插入一段 → 后面所有 index 偏移 → 全部判为变更**。即当前实现是"锚定序号"的 diff：对尾部追加友好，对头部插入最差。改进方向：锚定内容的对齐算法（类似 LCS 文本 diff），按纯内容 hash 匹配、允许错位。

## 设计原则小结

1. fail fast：越早拒绝越便宜；
2. 异步边界画在"数据安全落地"之后；
3. 消费端幂等 + 竞态窗口复查；
4. 前端多样、后端归一（一切 → Markdown）；
5. 切分器不信任自己（质检降级链）；
6. 相同文字+相同模型=相同向量，天然可缓存（但要小心 index 锚定的偏移问题）。
