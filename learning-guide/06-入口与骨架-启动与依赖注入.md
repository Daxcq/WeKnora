# 第 6 章 · 入口与骨架：启动、依赖注入、路由

进程从启动到能接客之间发生了什么。涉及 `cmd/server/main.go`（143 行）、`cmd/server/bootstrap.go`（125 行）、`internal/router/router.go`（305 行）、`internal/container/container.go`（1443 行，当字典查）。

## 第一幕：main.go——五分之四在讲"怎么体面地死"

启动三步（42–62）：

```go
c := container.BuildContainer(...)   // ① 装配 DI 容器
runStartupBootstrap(c)               // ② 一次性引导钩子
c.Invoke(func(cfg, router, ...) {...})  // ③ 取货并启动
```

`c.Invoke` 的魔法：**函数签名只写参数类型，容器自动把实例递进来**——不用 new 任何东西。

**优雅停机**（93–129）是可抄进自己项目的范本：

1. **订阅退出信号**（93–94）：`signal.Notify` 监听 SIGTERM/SIGINT（`docker stop` 发 SIGTERM）。没有它容器等 10 秒被 SIGKILL 硬杀，在途请求断头；
2. **先关监听器再排水**（101）：`listener.Close()` 立刻释放端口——新流量进不来，老流量排干（`server.Shutdown` 等在途请求完成，默认 30 秒）。滚动部署时下一进程可立即绑端口；
3. **第二次信号 = 强杀开关**（111–115）：再按一次 Ctrl+C → `server.Close()` 立即断开。**给操作者留逃生门**；
4. **打扫卫生**（123）：`resourceCleaner.Cleanup`——关数据库、flush 日志、协调 asynq 在途任务。

> 类比：优雅停机 = 餐厅打烊——摘"营业中"牌子（关 listener）、客人吃完（排干）、打扫厨房（清理）、锁门（退出）。直接拔电（SIGKILL）= 客人吃一半被轰走。

## 第二幕：container.go——全城工厂的总注册处

**DI 解决什么病**：手动构造 `KnowledgeHandler` 要new 一长串依赖且每个 handler 重复仪式。**DI 容器 = 自动装配车间**：

```go
must(container.Provide(initDatabase))                      // 登记：我会造数据库
must(container.Provide(repository.NewKnowledgeRepository)) // 登记（需要数据库）
must(container.Provide(service.NewKnowledgeService))       // ……
```

`Provide` 只登记造法不真造。`Invoke` 要 `*gin.Engine` 时 dig 沿依赖图**倒推**：路由器 → 40 个 handler → service → repository → 数据库 → 配置。**每类型单例、按需懒加载、循环依赖启动时报错**。

`router.go:28` 的 `RouterParams` 是"取货车单"标准写法：

```go
type RouterParams struct {
    dig.In                    // ← 让 dig 认领整个结构体
    Config           *config.Config
    KnowledgeHandler *handler.KnowledgeHandler
    // ……40 多个字段
}
```

`BuildContainer`（container.go:102）的**注册顺序就是分层地图**：基础设施（config/db/redis/file）→ 仓储层（~35 个 repo）→ 服务层 → handler → 路由。

**阅读技巧**：想知道某 service 依赖谁，看构造函数签名即可——dig 保证签名里的参数都被满足。1443 行的 container.go 当**字典**查。

**工厂落地**：`engine_factory.go:46` 返回闭包工厂，按向量库配置 switch 到 11 种引擎之一（62–78）。"配置 → 引擎实例"的翻译官——换 `RETRIEVE_DRIVER` 就换向量库的全部秘密。

## 加映：bootstrap.go——"最好的努力"哲学

`WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL` 机制（注释自问自答）：

- **为什么环境变量而非 CLI 子命令**：compose/k8s 设一次，首个该邮箱注册的用户自动成为系统管理员，零运维步骤；
- **幂等**：已是管理员 → no-op；
- **为什么敢一直留着**：**系统里已存在任何管理员时，变量不再授予权限**（109–114）——防 UI 撤销后被重启"复活"。把"提权后门"驯化成"首次开荒工具"。

文件头总原则：**引导钩子全部 best-effort，失败只警告绝不阻止启动**——配错环境变量的运维应该还能把服务拉起来修，而不是一个 typo 把部署变砖。与第 4/5 章"增强组件只降级"一脉相承：**启动路径上除命脉（数据库、端口）一切都可妥协**。

## 第三幕：router.go——洋葱的返乡演出

`r.Use(middleware.Logger())` 就是第 3 章的洋葱。**顺序即语义**——每层只能看见它包住的层：

```
CORS          ← 最外层：跨域预检第一个被问
RequestID     ← 发请求身份证（贯穿日志）
Language      ← 解析语言
Logger        ← 记耗时（在 Auth 外，401 也被记录）
Recovery      ← 兜 panic
ErrorHandler  ← 把 c.Error(err) 翻译成 HTTP 错误响应
──── 公开路由：/health、swagger、IM 回调、embed ────
Auth          ← 分水岭！之后全部要验 JWT / API Key
Langfuse      ← 观测（未配置时空操作）
/api/v1 组     ← 两百多条业务路由
```

三个值得抄的细节：

1. **`/health` 在 Auth 之前**（127）：健康检查必须免认证，否则负载均衡器没资格探测你；IM 回调用平台自己的签名验证，不走全局 Auth；
2. **`SetTrustedProxies`**（100）是真实安全事件的化石：Gin 默认信任所有代理的 `X-Forwarded-For`，攻击者伪造该头可绕过按 IP 限流的公开 embed 端点。修复 = 只信内网网段。**注释即事故报告**；
3. **`assertAPIKeyPoliciesMatchRoutes`**（275）：启动时校验 API Key 策略真的对应存在的路由，不匹配直接 panic——"过期模板会让所有 API Key 在那条路由上静默 403，宁可启动时炸"。**fail fast：错误暴露越早代价越小**。

## 加映：rbac.go——权限的四层阶梯

`rbacGuards`（113）做中间件工厂：`Viewer()/Contributor()/Admin()/Owner()` 四级（195–211），路由注册时挂：

```go
v1.GET("/knowledge-bases/:id/knowledge", guards.Viewer(), handler.List)     // 能看
v1.POST("/knowledge-bases/:id/knowledge", guards.Contributor(), ...)        // 能传
v1.DELETE("/knowledge-bases/:id", guards.Admin(), ...)                      // 能删
```

另一套：**API Key 能力位**（226–331 的 `apiKeyRetrieve`/`apiKeyIngest`/`apiKeyManageModels`…）——JWT 按"角色"授权，API Key 按"能力"授权（`apiKeyChat` 能对话不能管理）。两套凭证一个中间件统一裁决（225）。

## 串珠：一条请求的完整穿越

```
启动时：BuildContainer 装配一切 → NewRouter 织好洋葱 → 等在 :8080
请求：  listener 收包 → Gin 匹配 → 穿洋葱
        [CORS→RequestID→Language→Logger→Recovery→ErrorHandler→Auth→apiKey]
        → handler（守门）→ service（大脑）→ repository（方言）→ Postgres → 原路返回
```

在此仓库做功能开发 = 往这条链某一环插东西：新接口 = handler + service + repository + 一行路由注册；新横切能力 = 一个中间件。
